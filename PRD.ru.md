# PRD: собственная система платной подписки Telegram + WordPress

## 1. Цель проекта

Создать self-hosted систему для управления платным Telegram-чатом и связанными аккаунтами на WordPress без использования стороннего сервиса подписок.

Система должна принимать подтверждения оплат Stripe и PayPal, хранить историю платежей, управлять доступом в Telegram, активировать/деактивировать WordPress-пользователей и предоставлять владельцу наглядную панель управления в Google Sheets.

## 2. Пользователи и роли

### Владелец/администратор

- управляет подписками через Google Sheets;
- добавляет пользователей вручную и продлевает доступ;
- устанавливает whitelist;
- отзывает и восстанавливает доступ;
- просматривает статусы, платежи, ошибки и журнал действий.

### Клиент

- запускает Telegram-бота командой `/start`;
- получает ссылку на оплату или продление;
- получает приглашение в закрытый чат после подтверждения оплаты;
- получает напоминания об окончании подписки;
- может установить или восстановить пароль WordPress.

### Системные интеграции

- Telegram Bot API;
- Stripe Webhooks/API;
- PayPal Webhooks/API;
- Google Sheets API;
- WordPress REST API и собственный WordPress-плагин.

## 3. Принятые архитектурные решения

1. **Система принадлежит владельцу и запускается на его инфраструктуре.** Платные SaaS-сервисы управления подписками не используются.
2. **Backend является исполнительным центром.** Он принимает вебхуки, применяет правила доступа, вызывает Telegram/WordPress API и пишет журнал.
3. **База backend является источником истины** для идентичностей, подписок, платежей, прав доступа, команд и журнала. Google Sheets является административной проекцией и каналом ручных команд, но не источником платёжного или фактического статуса.
4. **Основной идентификатор Telegram — числовой Telegram ID.** Username используется только для отображения.
5. **Отзыв доступа не удаляет WordPress-пользователя.** Аккаунт блокируется, платные права снимаются, история сохраняется; восстановление возможно.
6. **Пароли не хранятся в backend или Google Sheets.** Для MVP бот может выдать сгенерированный постоянный пароль в личном сообщении Telegram; WordPress хранит только штатный хеш. Повторный запрос заменяет пароль.
7. **Платёжное состояние, ручной override и фактический доступ хранятся раздельно.** Приоритет: ручной запрет (`deny`) выше whitelist (`allow`), whitelist выше расчётного права по подписке. Без override доступ разрешён до максимума из подтверждённого `provider_paid_until` и журналируемого `manual_access_until` либо до конца согласованного grace period.
8. **Изменения внешних систем выполняются с eventual consistency.** Принятое событие сначала надёжно фиксируется в БД, затем отдельные идемпотентные операции синхронизируют Telegram, WordPress и Google Sheets; частичный сбой не откатывает подтверждённый платёж.

## 4. Основной жизненный цикл пользователя

1. Клиент открывает бота и нажимает `/start`.
2. Backend сохраняет Telegram ID и предлагает безопасно связать его с WordPress-аккаунтом через одноразовый токен из уже аутентифицированной WordPress-сессии либо подтверждение, отправленное самим WordPress на сохранённый email аккаунта. Совпадения email недостаточно для захвата существующего аккаунта.
3. Клиент оплачивает план через Stripe или PayPal.
4. Платёжный провайдер отправляет webhook.
5. Backend проверяет подпись по исходному телу запроса, атомарно сохраняет provider event и ставит его в очередь; повторная доставка подтверждается без повторного бизнес-действия.
6. Worker сверяет внешний объект при необходимости, не полагается на порядок webhook-событий и вычисляет `provider_paid_until` по оплаченному billing period провайдера, а не как «текущее время + длительность».
7. WordPress-аккаунт активируется или создаётся с указанной ролью.
8. Бот создаёт короткоживущую персональную ссылку с join request и отправляет её клиенту.
9. Бот одобряет запрос только для ожидаемого Telegram ID и отзывает ссылку после успешного вступления или истечения срока. Ссылка с `member_limit=1` без проверки ID не считается защищённой, поскольку её можно переслать.
10. Backend регулярно проверяет истекающие подписки и фактическое членство в чате.
11. Когда вычисленный `effective_access` становится `denied` и повторная проверка это подтверждает, система отправляет уведомление, удаляет пользователя из чата и блокирует вход на WordPress.

## 5. Google Sheets как панель управления

### Лист «Пользователи»

Обязательные поля:

- `telegram_id`;
- имя и username для отображения;
- `wordpress_user_id`;
- email/логин WordPress;
- роль WordPress;
- платёжный статус, ручной override и вычисленный статус доступа;
- дата начала, `provider_paid_until`, `manual_access_until` и вычисленный `effective_until`;
- способ оплаты;
- внешний ID клиента/подписки;
- `whitelist`;
- команда в поле «Действие»;
- уникальный `command_id`, причина, ожидаемый статус и состояние выполнения команды;
- результат последней операции;
- дата последней синхронизации.

Допустимые действия:

- `Создать/добавить`;
- `Продлить`;
- `Отозвать доступ`;
- `Восстановить доступ`;
- `Добавить в whitelist`;
- `Убрать из whitelist`;
- `Проверить`;
- `Повторить ошибку`.

### Лист «Платежи»

Содержит неизменяемую историю платежных событий: провайдер, ID события, пользователь, сумма, валюта, статус, дата, тип события и результат обработки.

### Лист «Ошибки»

Содержит correlation ID, интеграцию и операцию, безопасное описание ошибки, количество/время попыток и допустимое действие повторения без секретов и полного webhook payload.

### Лист «Dashboard»

Показывает:

- активных пользователей;
- пользователей, у которых осталось 7 дней;
- пользователей, у которых осталось 3 дня;
- просроченные подписки;
- пользователей в whitelist;
- последние успешные и неуспешные платежи;
- ошибки синхронизации;
- количество управляемых пользователей в Telegram/WordPress, общий `getChatMemberCount` Telegram и расхождение между общим и известным составом.

### Правила работы с таблицей

- доступ к таблице ограничен явным списком редакторов; системные, платёжные и журналируемые диапазоны защищены от ручного редактирования;
- команда выполняется только после проверки схемы строки и уникального `command_id`; право редактировать файл не заменяет серверную авторизацию команды;
- backend возвращает в таблицу результат операции или понятную ошибку;
- `command_id` атомарно регистрируется в БД до выполнения, поэтому повторное чтение и конкурентный запуск не дублируют действие;
- прямое редактирование статуса не должно автоматически считаться подтверждением оплаты;
- ручное продление создаёт неизменяемую adjustment-запись и меняет `manual_access_until`, но не перезаписывает `provider_paid_until`; whitelist также требует причины и автора;
- если нужен доказуемый автор, команда создаётся через аутентифицированный Apps Script/web app с проверенной Google identity; Drive Activity API используется только как дополнительный аудит файла, а свободно введённое поле `requested_by` не считается доказательством;
- внешние строки (имя, username, email, тексты ошибок) записываются как `RAW` и не интерпретируются как формулы.

## 6. Платежи и подписки

### Общие платёжные правила

- пользователь связывается с checkout/subscription через непрозрачный внутренний ID в server-side metadata/custom ID; email из webhook не используется как единственное доказательство личности;
- повторная команда оплаты не создаёт параллельную recurring-подписку: backend проверяет существующий pending/active контракт и возвращает текущий checkout/portal либо явную ошибку;
- деньги хранятся в минимальных денежных единицах вместе с валютой; внешний payment/subscription ID уникален в пределах провайдера;
- webhook handler быстро отвечает после проверки и надёжной записи события, а бизнес-обработка выполняется асинхронно;
- дедупликация учитывает и ID события, и бизнес-объект/тип события, поскольку один объект может породить несколько событий;
- события могут приходить повторно и не по порядку; перед отзывом доступа при сомнении выполняется сверка с API провайдера;
- отмена в конце периода не отзывает уже оплаченный доступ до `provider_paid_until`; для полного/частичного refund, reversal и dispute/chargeback должна быть утверждена отдельная политика.

### Stripe

- создание или использование recurring subscription;
- обработка `invoice.paid`, неудачной/требующей действия оплаты, изменения/отмены подписки, refund и dispute; `checkout.session.completed` само по себе не заменяет подтверждение успешного платежа для асинхронных методов;
- проверка подписи webhook по исходному телу запроса и зафиксированной версии Stripe API;
- поддержка retry/dunning через настройки Stripe и сообщения бота;
- Checkout для покупки и Stripe Customer Portal либо эквивалентный безопасный flow для обновления метода и отмены.

### PayPal

- подключается через отдельный адаптер с теми же внутренними статусами;
- обработка `BILLING.SUBSCRIPTION.CREATED/ACTIVATED/UPDATED/EXPIRED/CANCELLED/SUSPENDED/PAYMENT.FAILED` и `PAYMENT.SALE.COMPLETED/REFUNDED/REVERSED`;
- проверка подлинности webhook по исходному сообщению и заголовкам либо через официальный verify endpoint;
- единая запись подписки независимо от платёжного провайдера.

Внутренняя модель не смешивает разные оси:

- `billing_status`: `pending`, `active`, `past_due`, `suspended`, `cancelled`, `expired`;
- `payment_status`: `pending`, `paid`, `failed`, `partially_refunded`, `refunded`, `reversed`, `disputed`;
- `access_override`: `none`, `allow`, `deny`;
- `effective_access`: `allowed`, `grace`, `denied`;
- отдельный provisioning status для Telegram и WordPress: `pending`, `applied`, `retrying`, `failed`.

## 7. Telegram-функции

- `/start` — регистрация и привязка пользователя;
- `/status` — текущий статус и дата окончания;
- `/pay` — ссылка на оплату;
- `/renew` — продление;
- `/help` — инструкция;
- уведомление за 7 дней;
- уведомление за 3 дня;
- уведомление при неудачном платеже;
- ссылка на оплату после failed payment;
- создание короткоживущих invite-ссылок с join request, проверкой ожидаемого Telegram ID и отзывом ссылки;
- удаление просроченного пользователя из чата;
- при восстановлении после `banChatMember` — явный `unbanChatMember` перед новой ссылкой;
- обработка события самостоятельного выхода из чата;
- дедупликация Telegram updates по `update_id`, проверка webhook `secret_token` и явное включение `chat_member`/`chat_join_request` в `allowed_updates`;
- уведомление администратору об ошибках и важных изменениях.

Пользователь должен предварительно запустить бота, иначе Telegram не позволит отправлять ему личные сообщения.

Напоминания за 7/3 дня означают окончание доступа только для ручного срока или отменённой в конце периода подписки. Для active auto-renewal текст сообщает о предстоящем списании либо уведомление отключается согласно утверждённой политике; бот не предлагает создать вторую подписку.

Bot API не предоставляет полный список исторических участников чата. MVP должен использовать новый/очищенный чат либо получить исходный реестр Telegram ID от владельца. Reconciliation проверяет известных пользователей через `getChatMember`; dashboard отдельно показывает известных управляемых участников, общий счётчик и необъяснённую разницу, но не обещает определить личности неизвестных участников.

## 8. WordPress-функции

Собственный плагин должен предоставить защищённые операции:

- найти пользователя по email, логину или WordPress user ID;
- создать пользователя без передачи открытого пароля backend;
- назначить разрешённую роль;
- активировать аккаунт;
- заблокировать вход;
- снять платную роль/права;
- восстановить доступ;
- установить постоянный пароль при активации и вернуть его только как факт установки;
- вернуть результат операции и диагностическую ошибку.

Интеграция работает только по HTTPS с отдельным отзываемым Application Password/эквивалентом интеграционного пользователя с минимальными правами. Каждый endpoint имеет `permission_callback`, проверку capabilities, валидацию входа и защиту от повторного запроса. При блокировке уничтожаются активные WordPress-сессии, иначе уже вошедший пользователь сохранит доступ. Пароль не попадает в логи или Sheets и не возвращается WordPress API; backend передаёт его пользователю только в личном сообщении Telegram.

Нужно разделить роль WordPress и платный статус: whitelist и оплаченная подписка не должны давать административные права WordPress. Привязка существующего аккаунта требует доказательства владения, а разрешённые роли задаются server-side allowlist.

## 9. Надёжность, безопасность и ошибки

- секреты хранятся в переменных окружения/секрет-хранилище, не в таблице и не в Git;
- webhook-подписи проверяются до изменения данных;
- webhook-события обрабатываются идемпотентно;
- входящие события, команды, уведомления и внешние действия имеют уникальные ключи; транзакционный inbox/outbox и очередь с backoff/dead-letter предотвращают потерю работы между записью в БД и вызовом API;
- есть повторные попытки для временных ошибок API;
- при недоступности Telegram или WordPress пользователь не удаляется немедленно;
- перед удалением выполняется повторная проверка статуса;
- предусмотрен grace period после неудачного recurring-платежа;
- все ручные и автоматические действия попадают в audit log;
- админские команды разрешены только явному server-side allowlist числовых Telegram ID; username и значения из Sheets не являются авторизацией;
- удаление из Telegram и блокировка WordPress выполняются как отдельные операции с понятным статусом каждой.
- destructive access actions выполняются только по актуальному вычисленному праву и после reconciliation; более новое событие не может быть перезаписано запоздалым старым событием;
- персональные данные и webhook payload минимизируются и редактируются в логах; определены сроки хранения, удаление/экспорт данных и шифрование резервных копий.

## 10. MVP

В первую версию входят:

- один Telegram-чат;
- один план подписки;
- Stripe;
- Google Sheets как админ-панель;
- собственная база пользователей, платежей и событий;
- создание invite-ссылок;
- напоминания за 7 и 3 дня;
- удаление после перехода `effective_access` в `denied` по окончании оплаченного/ручного срока и применимого grace period;
- WordPress-плагин для активации/блокировки входа;
- whitelist;
- журнал операций;
- тестовый режим без реального удаления пользователей.

PayPal, несколько тарифов, купоны, реферальная программа и расширенная аналитика подключаются после проверки MVP.

## 11. Вне первой версии

- мобильное приложение;
- собственный платёжный шлюз;
- хранение карточных данных;
- автоматическое удаление WordPress-профилей;
- несколько независимых проектов/чатов;
- сложная CRM;
- массовые рассылки без ограничений и согласия пользователей.

## 12. Критерии приёмки

- [ ] Пользователь может запустить бота и получить статус.
- [ ] Успешный тестовый Stripe-платёж создаёт или активирует подписку.
- [ ] Повторный webhook не создаёт дубликат платежа и повторную подписку.
- [ ] Webhook-события, доставленные не по порядку, не сокращают уже подтверждённый оплаченный период и не вызывают ошибочный отзыв.
- [ ] Активный пользователь получает индивидуальную invite-ссылку.
- [ ] Пересланная invite-ссылка не даёт доступ другому Telegram ID; после восстановления ранее удалённый пользователь может снова вступить.
- [ ] В Google Sheets видны статус, дата окончания и результат последней операции.
- [ ] Команда `Продлить` из таблицы создаёт adjustment, пересчитывает `manual_access_until`/`effective_until` и не изменяет `provider_paid_until`.
- [ ] Повторный или конкурентный запуск одного `command_id` выполняет действие ровно один раз.
- [ ] Команда `Отозвать доступ` удаляет пользователя из Telegram и блокирует WordPress после успешной проверки.
- [ ] Команда `Добавить в whitelist` предотвращает автоматический отзыв доступа.
- [ ] Напоминания отправляются за 7 и 3 дня и не дублируются.
- [ ] Ошибка внешнего API видна в таблице и может быть повторена.
- [ ] В тестовом режиме реальные пользователи не удаляются.
- [ ] Открытые пароли и платёжные секреты нигде не сохраняются.
- [ ] Блокировка WordPress завершает существующие пользовательские сессии, а неподтверждённый Telegram-пользователь не может привязать чужой WordPress-аккаунт.
- [ ] Отмена в конце периода, failed payment, полный/частичный refund и dispute следуют утверждённой политике доступа.

## 13. Открытые решения перед реализацией

- зафиксировать Stripe как провайдер MVP и PayPal как отдельный post-MVP этап;
- определить точную систему WordPress: стандартные роли или конкретный платёжный/ membership-плагин;
- определить длительность grace period;
- определить формулы продления: provider period, ручное продление от `max(now, effective_until)` и поведение при смене провайдера;
- утвердить правила отмены, refund, reversal, dispute/chargeback и ручного возврата;
- определить роли администраторов Google Sheets и Telegram;
- выбрать механизм доказуемой атрибуции команд Google Sheets;
- выбрать инфраструктуру размещения и домен webhook;
- согласовать тексты уведомлений и часовой пояс отправки;
- согласовать валюту, налоги/чеки, пользовательские условия, privacy/refund policy и сроки хранения данных до production-платежей.
