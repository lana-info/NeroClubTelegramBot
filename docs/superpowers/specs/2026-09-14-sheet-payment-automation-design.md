# Автоматизация ручных платежей из Google Sheets

## Цель

Администратор вносит только Telegram ID и дату подтверждённой ручной оплаты.
Backend единожды фиксирует платёж, продлевает подписку на один календарный
месяц и сам пересчитывает доступ в Telegram и WordPress.

## Границы

- Google Sheets остаётся административным интерфейсом, а SQLite backend —
  единственным источником истины для оплаты, срока и доступа.
- Тариф в этом изменении только `monthly`: один календарный месяц.
- Whitelist остаётся единственным обычным ручным переключателем доступа.
- Возвраты, частичные возвраты и смена тарифа не меняют историческую строку
  оплаты и не входят в этот этап.

## Правило срока

Для подтверждённого платежа:

```text
base_until = max(current_provider_paid_until, paid_at)
new_provider_paid_until = add_calendar_month(base_until)
```

`add_calendar_month` сохраняет номер дня, если он существует в следующем
месяце, иначе использует последний день месяца. Например, 31 января становится
28 февраля в невисокосный год. Время всегда нормализуется к UTC.

## Данные и идемпотентность

Новая запись платежа хранится в `inbox_events` как провайдер `sheet` и имеет
неизменяемый `payment_id`, созданный Apps Script. Уникальность
`(provider, external_event_id)` не даёт повторной синхронизации добавить ещё
один месяц. Платёж содержит Telegram ID, дату оплаты, тариф `monthly` и
результат обработки.

Backend принимает только платежи с существующим пользователем. Пустой,
некорректный или неизвестный Telegram ID оставляет срок без изменений и
возвращает построчную ошибку для отображения в таблице.

## Представление Google Sheets

Вкладка `Платежи` получает следующие колонки:

| Колонка | Кто заполняет | Назначение |
|---|---|---|
| `payment_id` | Apps Script | Стабильный ключ записи, не редактируется |
| `telegram_id` | Администратор | Обязательный идентификатор клиента |
| `paid_at` | Администратор | Обязательная дата платежа |
| `plan` | Apps Script | Всегда `monthly` в этом этапе |
| `status` | Backend | `processed`, `duplicate` или `error` |
| `applied_until` | Backend | Рассчитанная дата окончания |
| `processed_at` | Backend | Время обработки |
| `error` | Backend | Понятная причина, если строка не принята |

Обычный ввод ограничен `telegram_id` и `paid_at`. Строка с пустым
`payment_id` получает UUID перед отправкой. После успешной обработки её
нельзя изменить так, чтобы изменить историю: тот же `payment_id` вернёт
прежний результат.

`Пользователи` становится проекцией backend: вручную допускается переключать
только `whitelist`, а даты, поставщик и статусы перезаписываются backend.
`Доступ к сайту` и `Dashboard` полностью выводятся backend и не служат
источниками команд. Существующие аварийные команды остаются отдельными от
whitelist.

## Синхронизация и миграция

1. Перед обновлением владелец создаёт копию Google Sheets как резервную.
2. Текущая вкладка `Платежи` переименовывается в `Платежи (архив)`. Её строки
   не импортируются как новые месяцы: у исторических записей нет достаточных
   данных, чтобы безопасно восстановить порядок и сроки продлений.
3. `importCurrentSnapshot()` остаётся разовой миграцией существующих сроков и
   больше не вызывается из периодического `syncAllSheets()`.
4. Периодическая синхронизация передаёт новые платежные строки и изменения
   whitelist, затем перезаписывает проекции `Пользователи`, `Платежи`, `Доступ
   к сайту`, `Dashboard` и `Настройки` из backend.
5. Успешный новый платёж ставит в очередь существующие операции выдачи или
   восстановления доступа. Повторная операция безопасна по ключу задания.

## Ошибки и безопасность

- Нет автоматического создания пользователя по платежу: это предотвращает
  ошибочное продление не того аккаунта.
- Ошибочная строка видна в `error` и может быть исправлена только до первой
  успешной обработки.
- Секрет `ADMIN_API_TOKEN` остаётся только в Script Properties и не попадает в
  таблицу, код или документацию.
- Серверные проверки должны покрыть повтор платежа, неизвестного пользователя,
  календарный переход 31-го числа и сохранение более позднего срока.

## Проверка результата

На тестовом пользователе с активным сроком до 31 января внести платёж от
15 января: срок станет 28 февраля, а не 15 февраля. Повторить синхронизацию и
проверить, что срок не изменился. Затем внести оплату для неизвестного ID и
убедиться, что строка получила ошибку без изменения пользователей и доступа.
