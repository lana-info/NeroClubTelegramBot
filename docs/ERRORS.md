# Исправления ошибок

## 2026-10-09: письмо о временно отсутствовавшем whitelist

Владелец получил уведомление Apps Script о syncAllSheets от
07.10.2026 22:49:14–22:49:16 EDT: `Missing header in Пользователи: whitelist`.
Это время сбоя в письме, а не время текущей диагностики.

Текущая проверка Google Sheets CellData: Пользователи!J1 содержит точную строку
whitelist без лишних пробелов; все 17 заголовков соответствуют USER_HEADERS.
Заголовки Доступ к сайту и Настройки также корректны. Данные и код не менялись.

Воспроизведение: реальный локальный SheetsSync.gs выполнен в Node VM с текущими
заголовками и двумя строками таблицы, backend заменён фиктивным отправителем.
syncWhitelists_ прошёл. Если убрать J1 только в памяти, получается точная
ошибка из письма, и whitelist-запрос к backend не отправляется. Реальных
запросов изменения данных при проверке не было.

Дополнительное подтверждение: журнал рабочего backend после времени сбоя
содержит 37 обращений к Sheets API. В 07.10.2026 22:50:46 EDT
`POST /internal/sheets/whitelist` вернул 200; затем users, payments, site-access,
dashboard, payment-corrections и settings также вернули 200 (до 22:50:53 EDT).
Это подтверждает успешное прохождение серверных этапов после сбоя; полный
журнал выполнения Apps Script не получен. Почему точный заголовок отсутствовал
именно во время исходного запуска, не установлено. Текущая ошибка не
воспроизводится, исправление таблицы и программного кода не требуется.

Document Control по-прежнему не содержит подключённых сессий. Текущий
облачный запуск syncAllSheets вручную не выполнялся: доступ к редактору
Apps Script отсутствует, а изменения через Sheets API не вызывают edit-trigger
(официальная документация: https://developers.google.com/apps-script/guides/triggers/installable).

## 2026-10-08: ключи бота не совпадают с сервером лицензий

Сценарий: сохранённый issued-ключ из бота должен проходить новую активацию
соответствующего продукта. Проверка по ID из таблицы выявила 35 несовпадений
среди 60 прежних ключей. Дополнительный поиск по суффиксу среди всех серверных
лицензий с полной проверкой scrypt исключил версию только об устаревшем ID:
те же 35 ключей не соответствуют ни одной текущей записи сервера.
После выпуска четырёх новых ключей результат: 64 проверено, 29 совпали,
35 не совпали; из проблемных 34 относятся к active, один к revoked.

Непосредственная причина: сохранённые ключи бота и текущие серверные
verifier рассинхронизированы. Вероятная предыстория: замена ключей на сервере
без обновления бота. В таблице есть отметки rotated; серверный
rotate_license_key меняет verifier, сохраняя ID и привязку устройства.
По сообщению владельца все предыдущие замены выполнял Codex. Точный порядок
операций не восстановлен: AdminService.audit_events хранится в памяти и не
входит в _persist_state. validate работает по license_id и устройству, поэтому несовпадение
старого ключа мешает новой активации, но само по себе не отключает уже
активированное приложение.

При первой диагностике массовый перевыпуск не выполнялся: владелец на запрос
о 34 ключах ответил вопросом о причинах. Затем владелец прямо поручил исправить
все ключи. Выполнено восстановление без изменения комбинаций, уже выдаваемых
ботом; отозванная лицензия сохранена отключённой.

Автоматическая проверка разрешений отклонила первоначальный широкий перенос
открытых старых ключей между контейнерами. Вместо этого выполнена разрешённая
проверка verifier: открытые ключи остаются внутри бота, наружу выводятся только
результаты. Этот способ подтвердил проблему без передачи открытых ключей.

Для двух согласованных новых пользователей отдельно созданы четыре реальные
бессрочные лицензии. LicenseApi activation/validate и клиентская проверка
подписи прошли в откатываемых транзакциях. Проверка кнопки «Мои ключи» на копии
базы прошла после исправления неверного ожидания тестового скрипта:
display_expiry возвращает «бессрочный», а не «бессрочно». Продуктовый код для
этой проверки не менялся; сообщения реальным пользователям не отправлялись.

Восстановление: подтверждённая рассинхронизация → серверные HMAC, salt,
verifier и suffix 34 лицензий согласованы с ключами бота → полная проверка
activate/validate и подписи клиента в транзакции с откатом тестовых устройств
→ 34/34 прошло сначала с полным откатом, затем перед commit. Снимки всех
остальных полей лицензий, прав, назначений модулей и устройств совпали.
Для 29 остальных ключей выполнена отдельная проверка того же протокола без
изменения ключей, 29/29 прошло. Всего 63 действующие лицензии проверены.
Использовался реальный LicenseApi и Python LicenseClient с закреплённым
публичным ключом; сам Rust-клиент Video и GUI приложений не запускались.

Один ключ, ранее issued в боте при revoked на сервере, переведён в revoked
в SQLite. Полное сравнение app_keys подтвердило сохранность остальных ключей;
integrity_check/FK-check прошли. Обработчик «Мои ключи» на копии базы проверен
для 32 владельцев: 59 ключей выдаются 30 пользователям, два пользователя с
истёкшей подпиской не получают оставшиеся четыре клубных ключа. Один из них
также имеет ручной deny; эти бизнес-ограничения сохранены.

Закрытые резервные копии до записи:
`/var/lib/license-service/artifacts/backups/owner-key-restore-20261008T032319Z/before.json`
и `/app/data/backups/owner-key-registry-20261008T032331Z/nero-before.db`.
Открытые ключи для восстановления и клиентских проверок передавались только
между ботом и его сервером лицензий в памяти, по прямому поручению владельца;
в файлы и вывод инструментов не записывались.

Повторный полный аудит после записи: 63 issued-ключа, 63 совпадения с активным
серверным реестром, ноль ошибок. В Google Sheets проверены 64 строки: 63 issued
и одна revoked; сроки и типы отражают сервер. HTTPS health вернул 200, оба
контейнера healthy. Для последующих изменений добавлена read-only проверка
`python3 tools/check_license_registry.py`: 63/63 прошло, секреты не выводятся.
README требует её успешного завершения и отдельного теста activate/validate
с подписью перед завершением операции изменения ключей. Автоматическая
синхронизация ротаций между независимыми сервисами не добавлялась.

## 2026-10-02: оплаченный доступ возвращался в Denied

Причина: у пользователя Telegram ID 482450182 сохранён `access_override=deny`
при подтверждённой оплате и `provider_paid_until=2026-10-30T00:00:00+00:00`.
Telegram-бана нет. Происхождение запрета не установлено: связанных записей
в журнале команд и аудите до исправления не найдено. `access` вычисляется
сервером; синхронизация заменяет ручное Active результатом этого расчёта.

Исправление разрешено пользователем в чате: снят только ручной запрет
(`deny` → `none`). До изменения создана закрытая SQLite-копия в
`/opt/bots-stack/nero-club-backups/access-482450182-20261002/nero.db`.
Транзакционная проверка подтвердила: кроме `access_override` и служебного
`updated_at` этой записи данные всех таблиц сохранились; после проверки
добавлена запись аудита `clear_access_override`.

Результат: `effective_access=active`, экспорт строки для таблицы также
возвращает `access=active`, срок оплаты не изменён. Обновление самой
Google-таблицы и пользовательский сценарий Telegram не проверялись.

## 2026-10-07: email и ручной срок исчезают из таблицы

Причина в локальном коде: `syncAllSheets()` не импортирует правки профиля,
а `writeBackendRows_()` очищает и заново заполняет экспортируемые строки.
Обработчик команд передаёт только ручной срок при явном `action=extend`;
email не передаётся. Поэтому прямой ввод в экспорт не является сохранением.
README ошибочно обещал периодический импорт правок; описание исправлено.
Облачная версия скрипта не прочитана, совпадение с локальной не подтверждено.

Дополнительная причина отказа ручного доступа у новых пользователей:
`effective_access()` возвращал denied до проверки manual_access_until,
если отсутствовала запись subscriptions.

Исправление: отдельная форма email/ручного срока и защищённый частичный PATCH
по Telegram ID с проверкой значений и аудитом до/после. Пустые поля формы
не отправляются; произвольные поля сервер отклоняет. Платежи не меняются.
Расчёт доступа теперь учитывает ручной срок без наличия подписки, сохраняя
приоритет ручного запрета и Telegram-бана. Если сохранение прошло, а обновление
таблицы отказало, форма сообщает о сохранении на сервере отдельно.

Проверка: до реализации все 14 новых HTTP-сценариев возвращали 404 вместо
ожидаемого поведения. После реализации общий pytest вне песочницы: 115/115
за 13,80 с. Оба Node-набора форм прошли, включая частичный ввод, ошибку связи,
смену пользователя, сообщение после сбоя обновления и показ ручного срока.
HTTP-проверки в песочнице вновь зависли при входе в синхронный обработчик;
см. запись о TestClient выше. Поддержка PATCH UrlFetchApp сверена с официальной
документацией: https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app.

Статус: только локальное исправление. Новый backend и облачный Apps Script
не опубликованы, реальная таблица не проверена. Подключённых Document Control
сессий нет. Прямые правки экспортируемых ячеек по-прежнему не сохраняются;
новый рабочий путь после публикации будет через кнопку формы.
